# Query schema (v4)

The record a query is stored as, field by field. `CURRENT_SCHEMA_VERSION` is **4**, declared in
[`src/constants.js`](../src/constants.js); the vocabularies and the validation rules below are
enforced by [`src/domain/validate.js`](../src/domain/validate.js), which is the authority for
everything on this page.

Schema v4 exists because until it landed a record had eleven fields and not one of them was
detection metadata, so the library could not answer either of the questions that justify keeping
one: *what is my ATT&CK coverage*, and *is this rule still valid*. Technique IDs could only be
smuggled into free-text tags, where `T1059.001` and `T1059.01` are indistinguishable and neither
can be validated.

**The whole detection block is optional.** A v3 record — one with none of it — still validates
untouched, which is what allows the fields to be filled in over time rather than in one migration.

## Core fields

| Field | Type | Required | Accepted values and bounds |
| --- | --- | --- | --- |
| `id` | string | yes | UUID v4. Generated by the client; the API generates one if a create arrives without it, and bounds a supplied one at 200 characters. |
| `name` | string | yes | 1–200 characters, trimmed. |
| `query` | string | yes | 1–50 000 characters. The KQL body, stored verbatim including newlines. |
| `description` | string | no | Empty by default. The SPA allows 10 000 characters, **the API rejects anything over 1 000**, so 1 000 is the real limit for anything that reaches the store. |
| `category` | string | no | One of `Detection`, `Hunting`, `Investigation`, `Monitoring`, `Reporting`, `Enrichment`, `Utility`. Defaults to `Utility`. This is analyst intent, and it is orthogonal to `queryType` below. |
| `table` | string | expected | 1–200 characters. Free text, not an enum — the store has to hold custom and ASIM tables it has never heard of. Absent or empty is **reported as an error but does not reject the record**: `validateQuery` returns `valid: false` and substitutes `Custom`, so the query is still storable. The editor's table selector defaults to `Custom`; `detectTableFromQuery` derives it from the query body during the v2 → v3 migration and for the linter, but it does not overwrite what the editor was told. |
| `tags` | string[] | no | At most 20, each at most 50 characters. Free text. Blank entries are dropped, the rest trimmed. |
| `favorite` | boolean | no | Defaults to `false`. Stored as INTEGER 0/1 in SQLite. |
| `usageCount` | integer | no | Non-negative. Incremented when a query is copied; an upsert keeps the larger of the two sides. |
| `created` | string | no | ISO 8601. Set on first write and never changed afterwards, including by an upsert. |
| `updated` | string | no | ISO 8601. Decides who wins an upsert, and backs the optional precondition on `PUT`. |
| `parentId` | string \| null | no | UUID v4 of the query this was forked from, or `null`. **Not a foreign key**: deleting a parent neither cascades to nor blocks its forks, so a `parentId` that resolves to nothing is an expected state and renders as an orphaned fork. A value that is not a UUID is dropped rather than failing the record. |
| `parentName` | string | no | ≤ 200 characters. The parent's name **at fork time**, not a live reference. It is what lets an orphaned fork still say what it came from, so it is correct for it to go stale when the parent is renamed. |

**Lineage sits outside the v4 detection block.** `parentId` and `parentName` are their own SQLite
columns (`parent_id`, `parent_name` in `api/db.js`), assigned in `toFrontend` *after* the detection
metadata is spread onto the record — see [How it is stored](#how-it-is-stored) — so they never
appear inside `metadata` and never reach the Sentinel or ATT&CK Navigator exports. A fork is not
detection metadata about the query; it is a fact about where the record came from, and none of the
export formats have a field for that.

Fork creation is client-side only: `src/domain/lineage.js`'s `makeFork` deep-clones the parent
(inheriting its full v4 detection block — severity, ATT&CK mapping, everything) and overrides `id`,
`created`, `updated`, `usageCount` (0), `favorite` (false), `tags` (a fresh array) and the two
lineage fields. Nothing is written until the fork is saved like any other query.

## Detection metadata

Every field here is optional and every one is validated against a fixed vocabulary or a pattern.

| Field | Type | Accepted values |
| --- | --- | --- |
| `queryType` | string | `AnalyticsRule`, `NRT`, `Hunting`, `Investigation`, `Workbook`. What the query is *for*, which decides how it would be deployed — as opposed to `category`, which is how an analyst files it. |
| `severity` | string | `Informational`, `Low`, `Medium`, `High`, `Critical`. Sentinel's own scale, so the Sentinel export passes it through unchanged. |
| `confidence` | string | `Low`, `Medium`, `High`. How much the author trusts the logic, which is not the same question as how bad a true positive would be. |
| `platform` | string[] | `Windows`, `Linux`, `macOS`, `Azure`, `AWS`, `GCP`, `Office365`, `Identity`, `Network`. At most 32, de-duplicated, order preserved. Feeds the Navigator layer's platform filter. |
| `attack.tactics` | string[] | The 14 MITRE ATT&CK Enterprise tactic slugs, in kill-chain order: `reconnaissance`, `resource-development`, `initial-access`, `execution`, `persistence`, `privilege-escalation`, `defense-evasion`, `credential-access`, `discovery`, `lateral-movement`, `collection`, `command-and-control`, `exfiltration`, `impact`. Slugs, not Sentinel's PascalCase — the export converts. |
| `attack.techniques` | string[] | `Txxxx` or `Txxxx.yyy`, anchored: `T1059` and `T1059.001` are accepted, `T1059.01` is rejected rather than stored. At most 32. |
| `dataSources.connectors` | string[] | Free text, at most 20 entries of 100 characters. Sentinel connector IDs, e.g. `MicrosoftThreatProtection`. Not an enum, because the connector catalogue changes faster than this repository does. |
| `dataSources.tables` | string[] | Free text, at most 30 entries of 200 characters. The tables the query reads — more than the single `table` field can hold once a query joins. |
| `entityMappings` | object[] | At most 10. Each is `{ entityType, identifier, columnName }`. `entityType` must be one of `Account`, `Host`, `IP`, `URL`, `FileHash`, `File`, `Process`, `Mailbox`, `MailMessage`, `CloudApplication`, `AzureResource`, `DNS`, `RegistryKey`, `Malware`; `columnName` is required; `identifier` is optional and defaults to an empty string. Both strings are trimmed to 100 characters. |
| `falsePositives` | string[] | At most 20 entries of 500 characters. What legitimately trips this query, in prose. |
| `tuningNotes` | string | At most 2 000 characters. What to baseline before enabling it. |
| `references` | string[] | At most 20. `http:` and `https:` URLs only, parsed with `new URL()` — a `javascript:` or `data:` reference is rejected, since this field is a link and not a script sink. |
| `lookback` | string | A KQL timespan literal: `\d+(\.\d+)?` followed by `d`, `h`, `m`, `s` or `ms`. `7d`, `90m`, `1.5h`. |
| `version` | string | Three-part semver, e.g. `1.2.0`. Per-rule versioning, carried into the Sentinel export. |
| `lastValidated` | string | ISO calendar date, `YYYY-MM-DD`. The review cadence: when someone last confirmed this still works. |
| `author` | string | At most 100 characters, trimmed. |
| `license` | string | At most 100 characters, trimmed. Spelled the American way because it is a schema field, not prose — see the naming rule in [CONTRIBUTING.md](../CONTRIBUTING.md#code-style). |

## What "invalid" does

`validateQuery` returns `{ valid, errors, sanitized }`, and the three are not redundant:

- **Only `id`, `name` and `query` can reject a record.** An error in any of those returns
  `sanitized: null` and nothing is stored.
- **Everything else is sanitised, and the problem is reported.** An unknown tactic, a malformed
  technique ID or a `ftp://` reference produces a message in `errors` and the offending value is
  left out of `sanitized`; the valid entries around it survive. This is deliberate: a bad ATT&CK
  ID in one field is not a reason to lose the query body someone just wrote.
- **Absent is never an error.** Only a *present but wrong* value produces a message.

So `valid === false` with a non-null `sanitized` means "we can store this, but you should look at
`errors` first", which is exactly what the import preview reports per item.

## How it is stored

SQLite is the source of truth. `api/db.js` creates:

```sql
CREATE TABLE IF NOT EXISTS queries (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  query       TEXT NOT NULL,
  description TEXT DEFAULT '',
  category    TEXT DEFAULT 'Utility',
  table_name  TEXT DEFAULT '',
  tags        TEXT DEFAULT '[]',      -- JSON array of strings
  favorite    INTEGER DEFAULT 0,      -- 0 | 1
  usage_count INTEGER NOT NULL DEFAULT 0,
  metadata    TEXT NOT NULL DEFAULT '{}',   -- JSON: the v4 detection block
  created     TEXT NOT NULL,          -- ISO 8601
  updated     TEXT NOT NULL           -- ISO 8601
);
```

The detection block is **one JSON column, not seventeen columns**. It is optional, it is only ever
read as a whole, and all filtering happens client-side once the SPA has loaded the store — the same
reasoning that has applied to `tags` since the beginning. `api/db.js` carries additive `ALTER TABLE`
migrations for `usage_count`, `metadata`, `parent_id` and `parent_name` so a database created by an
older build is upgraded in place on startup. `parent_id` and `parent_name` are not declared with a
`REFERENCES` clause even though the connection opens with `foreign_keys = ON` — deliberately: a
foreign key would force a choice between blocking a parent's deletion and cascading it to every
fork, and both are wrong here. SQLite also refuses `REFERENCES` inside `ALTER TABLE ADD COLUMN`
in any case, so an additive column could not have one.

Over the wire the block is **flat**. `toFrontend` spreads `metadata` back to the top level, because
that is the shape `validateQuery` works in, so `GET /api/queries` returns:

```json
{
  "id": "7ddf7202-…", "name": "Encoded PowerShell command line", "query": "…",
  "severity": "High", "queryType": "Hunting",
  "attack": { "tactics": ["execution", "defense-evasion"], "techniques": ["T1059.001", "T1027"] },
  "lookback": "7d", "created": "…", "updated": "…"
}
```

The write path accepts either shape — nested under `metadata`, or spread across the top level — and
top-level keys win. Without that, the API would emit a shape it could not itself consume and any
client that read a query and wrote it back would silently drop every detection field.

## The API validates size, not vocabulary

`api/validate.js` bounds the serialised detection block at 20 000 characters and rejects a
non-object, and that is all it does with it. The vocabularies above are enforced in the SPA. A
direct caller can therefore store a malformed technique ID:

```console
$ curl -s -X POST http://localhost:8080/api/queries -H 'Content-Type: application/json' \
    -d '{"name":"bad tech","query":"SigninLogs | take 1","table":"SigninLogs",
         "attack":{"techniques":["T1059.01"]}}'
{"id":"c56b9a55-…","attack":{"techniques":["T1059.01"]},…}   # HTTP 201
```

That is a real gap, stated here rather than glossed over. It does not reach the store through the
UI or through the app's own import, both of which run `validateQuery` first, and it costs nothing
worse than a technique that will not match in the Navigator layer.

## Migration

`migrateData` in [`src/domain/migrate.js`](../src/domain/migrate.js) runs the chain on any imported
blob that carries a `schemaVersion`, and on the cached copy in `localStorage` at load.

| Step | What it does |
| --- | --- |
| v1 → v2 | Adds `severity` and `tags`. |
| v2 → v3 | Removes `severity` and `platform`, detects `table` from the query body, and maps the old categories: Threat Hunting → Hunting, Incident Response → Investigation, Identity & Access → Detection, Network → Detection, Compliance → Reporting, Custom → Utility. Anything unrecognised becomes Utility. |
| v3 → v4 | Promotes ATT&CK technique IDs out of free-text tags. A tag matching `tNNNN` or `tNNNN.NNN` (case-insensitive) becomes an `attack.techniques` entry, normalised to `T1059.001`, and is removed from `tags`; every other tag is left alone. **Nothing is invented** — a query with no technique tags comes through unchanged. |

Data written by a **newer** build is refused rather than migrated: `migrateData` returns
`{ tooNew: true, … }` and the caller loads it read-only. It used to fall through every branch and
return the blob restamped as the current version, and the caller wrote that downgrade back to
storage — destroying the version marker so a later migration would never run.
